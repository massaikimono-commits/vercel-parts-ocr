# 車両管理アプリ 実用化ロードマップ

## 目的
車検証読取を入口に、顧客・車両・入出庫・部品・整備・記録簿・印刷を1台の車両IDで一貫管理する。

## 基本方針
- Supabaseを正式データ、localStorageは一時キャッシュとして扱う。
- OCRは最後の手段。QRやPDFテキストレイヤーなど、より確実な情報源を優先する。
- 読取値は `value / source / confidence / original_document_id` を持つ。
- 原本PDF・写真を保存し、後から「なぜこの値になったか」を追跡できるようにする。
- 読取・自動判定・印刷は分離し、各機能を独立してテスト可能にする。

## 車検証読取の優先順位
1. QRあり: QRを正式情報源として採用し、不足項目だけ補完する。
2. QRなし + 文字レイヤーPDF: PDF.jsで文字と位置を直接取得し、表構造を解析する。原則OCR 0pass。
3. スキャンPDF: 車検証の枠・セルを検出し、必要セルのみOCRする。
4. 写真: 台形・傾き補正後、セル検出して必要項目のみOCRする。

## 本番データ構造（候補）
- customers: 顧客
- vehicles: 車両マスタ
- vehicle_documents: 車検証PDF/写真の原本と版管理
- vehicle_document_values: 読取値、取得元、信頼度
- work_orders: 入庫・整備案件
- appointments: 引取・納車・来社・出張予定
- parts_receipts: 部品伝票原本
- parts: 部品名称・個数・定価・仕入れ
- inspection_records: 点検整備記録簿
- inspection_results: 点検結果・記号・測定値
- print_templates: 帳票ごとの印字位置
- print_history: 印刷履歴
- photos: 車両・整備写真
- audit_logs: 更新履歴

## 実用化に必要な品質対策
### 1. 回帰テスト
メーカー・車種・入力方式ごとに正解データを保存し、修正のたびに既存ケースが壊れていないか自動確認する。

最低セット:
- QRありPDF
- QRなし文字レイヤーPDF
- スキャンPDF
- iPhone写真
- 普通車 / 軽 / 貨物 / HV / EV / ディーゼル

### 2. 読取信頼度
重要項目（登録番号、車台番号、型式、満了日など）は、低信頼時に勝手に確定せず確認対象にする。

### 3. 原本保存
車検証・部品伝票・記録簿の原本をSupabase Storage等に保存する。

### 4. 監査ログ
自動読取値、手修正値、更新者、日時を残す。

### 5. 帳票テンプレート
帳票ごとに `field / x / y / width / height / fontSize` を保存し、用紙追加時にコード改修を最小化する。

## 開発順序
### Phase 1: 車検証読取を安定化
- QRなしPDFをOCR 0passで高精度取得
- QRありPDFとの統合
- 写真・スキャンPDFのフォールバック
- 回帰テスト基盤

### Phase 2: 車両マスタを正式化
- 車検証読取結果をvehicle_documents経由でvehiclesへ反映
- 同一車両判定
- 原本・更新履歴保存

### Phase 3: 入出庫・部品を車両IDへ統合
- work_orders導入
- partsをwork_order/vehicleへ紐付け
- スケジュール管理

### Phase 4: 記録簿ルールエンジン
- 車種・燃料・駆動方式・部品交換情報から点検記号を自動判定
- 不明項目は空欄として人が確認

### Phase 5: 印刷基盤
- 点検整備記録簿
- 指定整備記録簿
- 部品用紙
- 1日スケジュール

## 現在の最優先
QRなし文字レイヤーPDFについて、OCRへ戻さずPDF構造だけで主要項目を正確に取得すること。現在のトヨタPDFを最初のゴールデンデータとして固定し、以後の変更で精度が落ちないようにする。
