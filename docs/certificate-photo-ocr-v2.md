# 車検証 写真OCR v2 設計

## 目的
QRなしPDFで確立した「確実な情報源を優先し、OCRは必要な時だけ使う」方針を写真にも適用する。
写真入力ではOCRエンジン単体の性能だけに頼らず、撮影品質判定・台形/傾き補正・画像前処理・レイアウト認識・複数候補統合・車両情報の整合性検証を一つのパイプラインとして扱う。

## 基本方針
1. PDF文字レイヤーのルートは変更しない。
2. 写真/スキャン画像だけを新しい Photo OCR v2 に通す。
3. 現在のTesseract.jsはフォールバックとして残す。
4. 高性能OCRは provider adapter を介して交換可能にし、特定ベンダーへ密結合しない。
5. 車検証の原本画像には個人情報が含まれるため、外部OCR利用時のAPIキーはサーバー側だけに保持する。
6. 読取値は value/source/confidence を持ち、低信頼値は自動確定しない。

## パイプライン
### Stage A: 撮影品質ゲート
- 解像度不足
- ピンぼけ
- 白飛び/黒つぶれ
- 強い反射
- 車検証が画面外
- 極端な傾き

不良時はOCRを開始せず、撮り直し理由を画面に表示する。

### Stage B: 文書補正
- EXIF向き補正
- 車検証四隅検出
- 台形補正
- 自動回転/傾き補正
- 余白除去
- グレースケール
- 局所コントラスト補正
- 必要時のみ2〜3倍拡大

### Stage C: OCR
優先候補:
- ドキュメント向けクラウドOCR（日本語、文字座標、confidence対応）
- 自前OCRサーバー（PaddleOCR等）
- Tesseract.js（既存フォールバック）

### Stage D: レイアウト/セル解析
全文文字列から正規表現だけで探さない。
車検証の見出し・行・列・セル位置を使い、
- 登録番号
- 日付
- 車台番号
- 型式/原動機
- 重量/寸法/軸重
- 使用者/住所
などを構造単位で取得する。

### Stage E: 候補統合・整合性検証
- 車台番号と型式系列
- 車両重量と軸重合計
- 車両総重量 >= 車両重量
- 軽自動車の寸法上限などの常識範囲
- 日付の前後関係
- 燃料/車種の辞書

高信頼候補のみ確定し、不明は空欄にする。

## OCR provider adapter
アプリ本体は provider 固有レスポンスを直接扱わず、下記の共通形式へ変換する。

```ts
type OcrToken = {
  text: string;
  confidence: number;
  box: { x: number; y: number; w: number; h: number };
};

type OcrResult = {
  provider: string;
  width: number;
  height: number;
  tokens: OcrToken[];
  elapsedMs: number;
};
```

これにより Azure / Google / PaddleOCR / Tesseract を同じ後段解析で比較できる。

## 実用化の評価方法
同じ原本画像を各OCRエンジンへ通し、30項目前後の車検証正解データに対する一致率を測る。
比較指標:
- core項目完全一致率
- 全項目完全一致率
- 誤確定率（空欄より重大）
- 処理時間
- 1枚あたりコスト

最低でも「スズキ写真」「別車両写真」「斜め撮影」「暗所」「反射あり」をゴールデンケース化する。

## 実装順
1. 撮影品質ゲート
2. 文書補正/画像前処理
3. provider adapter
4. 高性能OCRを1社つなぎ、TesseractとA/B比較
5. 写真用レイアウト解析
6. 回帰テストへ写真ケース追加
7. 最良providerを本番優先、その他をフォールバックへ

## セキュリティ
- OCR APIキーを NEXT_PUBLIC_* に置かない。
- OCR呼び出しはNext.js server route等を経由する。
- Supabase Storageはprivate bucketを前提にする。
- 外部OCRへ送る原本の保存期間/ログ保持を確認し、本番前に運用方針を決める。
